# 微信粘贴兼容性踩坑手册

> 以下是橙墨开发过程中**真实踩到、逐个用公众号编辑器实测验证**过的坑。每条按「现象 → 根因 → 解法」组织。如果你在做任何「HTML → 公众号」的工具，这份手册大概率帮你省掉几个深夜。
>
> 微信的解析行为是黑盒且会变。遇到新坑欢迎开 issue 附最小复现 HTML，持续补充。

## 1. 行高一律输出 px

- **现象**：`line-height: 1.8` 粘贴后被判「行高小于字体大小」。
- **根因**：官方检测按 `内容高 ÷ 矩形数 < 0.95 × 字号` 估叠字，无单位值会被当成 **1.8px** 的字面量参与估算——数学上必然触发误判。
- **解法**：渲染器统一走 `lh(字号, 倍率)` 函数，**所有行高输出带单位的 px 实值**，绝不写无单位数字。

## 2. 正文不写任何 font-family

- **现象**：输出的 `font-family: serif` 这类「无害」声明也会触发样式白名单违规。
- **根因**：官方样式白名单**只有一条字体链**：`"mp-quote", PingFang SC, system-ui, -apple-system`。白名单是穷举式的——`serif`、`sans-serif`、宋体、微软雅黑，全都不在链上。
- **解法**：正文**完全不输出 font-family**，交给微信回退到默认字体链。想要「宋体感」只能靠截图或图片实现（且需接受模糊）。橙墨连主题系统也不提供字体选项，就是这个原因。

## 3. 复制必须走 copy 事件 + 净化

- **现象**：预览里明明干净，粘贴进公众号却报「结构异常」，payload 里多出一堆没写过的样式。
- **根因**：`document.execCommand('copy')` 复制选区时，浏览器走 `annotate-for-interchange` 序列化，会把**本页级联计算后的样式**写进剪贴板——`text-align:start`、`font-family`（整条计算链！）、`orphans`、`widows`、`text-indent`……其中 font-family 一项就足以触发白名单违规（见第 2 条）。
- **解法**：
  1. 监听 `copy` 事件，在事件里用 `clipboardData.setData('text/html', html)` **自建 HTML payload**，不经过选区序列化；
  2. setData 前先**净化**：`start`→`left` 归一、删全部 `font-family`、删浏览器附加属性。

## 4. 所有直接文本节点包 span leaf

- **现象**：段落里只要有一次 `<strong>`，官方检测必报「行高叠字」，**单行纯文本段落也报**，无论行高调多大。
- **根因**：官方 §2.3.2 的矩形数取 `getClientRects().length`，而该方法对**一行内的每个行内片段各返回一个矩形**——加粗、链接、换色的 span 都会把矩形数撑大。官方规范期望的结构本身就是 `<section><span leaf="">文字</span></section>`，且该检测的兜底分支只查「有直接文本子节点的块」。
- **解法**：输出前用 `wrapTextRuns` 把**所有直接文本节点包进 `<span leaf>`**。实测：同一篇 30 段真文，不包时 official 口径报 27/30/23 处，包上后 0 处。这条是渲染管线的底层结构约定，详见 [self-check.md](self-check.md)。

## 5. 空标签会被剥掉，条内塞 nbsp

- **现象**：4px 高的橙色分割条（`<span>` 实现）在编辑器里好好，粘贴到公众号后**只剩一段空隙，条没了**。
- **根因**：微信粘贴解析会**剥掉空标签**（无文本内容的内联元素直接删除）。
- **解法**：条内塞 `&nbsp;` 占位；配合 `font-size:4px; line-height:4px; overflow:hidden` 把 nbsp 的副作用锁死、保住基线对齐。同理，一切「纯装饰性内联元素」都必须有内容或占位。

## 6. 引用块按行分行

- **现象**：Markdown 里连续多行 `>` 引用，粘贴后微信把行间语义合并，多行变一段。
- **根因**：标准 Markdown 把块内 softbreak 合为软换行，微信对 `<br>` 之外的换行语义不可靠。
- **解法**：引用块内的 softbreak 直接渲染成 `<br>`（连续 `>` 行在块内按行分行）；嵌套引用按深度计数递归处理。**只对引用块这么做**——正文段落保持标准 Markdown 合段语义，否则正常段内换行会被破坏。

## 7. 模块上下留白对称

- **现象**：带底色的提示块/模块贴进公众号后「下松上紧」——模块与上文间距正常，与下文却多出一截（或反之）。
- **根因**：容器 `padding` 叠加**最后一个子元素的 `margin-bottom`**：块内最后一段的段距会叠进容器 13px 的 padding，视觉上底下多空一截。
- **解法**：输出前对带底色模块（识别特征如 `border-radius:0 6px 6px 0` 的左条卡）做 `polish()`：**清零容器最后一个子元素的 margin-bottom**，让容器 padding 独立决定内边距。

## 8. 徽章一律白字，底色须过 AA

- **现象**：深色字放在彩色徽章上「发闷」，白字放在亮色底上对比度不足。
- **根因**：小面积色块上的文字天然缺乏上下文冗余，对比度要求实际比正文更苛刻；而「白字徽章」的底色必须够深才能过 WCAG AA。
- **解法**：徽章**一律白字**（灰阶字在彩色底上显脏），底色逐个计算对比度定值。橙墨默认主题五色提示块徽章的实测值：

| 徽章 | 底色 | 白字对比度 |
|------|------|-----------|
| 说明 | `#d03800` | 4.94 |
| 注意 | `#a06300` | 4.91 |
| 重点 | `#c93600` | 5.23 |
| 提示 | `#8c5a2b` | 5.81 |
| 警告 | `#cf3b2a` | 4.89 |

全部 ≥4.5:1（AA）。方法论见 [theming.md](theming.md)。

## 9. 不用 flex / grid，table 保稳

- **现象**：编辑器预览里排好的多列布局，粘贴后错位或被拍平。
- **根因**：微信编辑器会**过滤 flex / grid 布局属性**。
- **解法**：多列结构用 `<table>`（配 `cellspacing=0` 内联边距）实现——这是各类公众号排版工具的通行做法。橙墨的结构化模块全部基于 table / 块级堆叠，不使用 flex / grid。

## 10. 其他平台行为备忘

逐条实测过、影响设计决策的平台行为：

- **不支持锚点跳转**：`<a href="#fn1">` 的文内跳转无效 → 脚注用「正文上标 + 文末参考块」的形态（见橙墨的被动脚注），放弃跳转、保住来源；
- **外链图片会被转存**：第三方图床的图可能被微信转存或防盗链拦截 → 橙墨不做图床集成，图片走公众号后台素材库上传；
- **空行即分段**：贴进去的 HTML 建议每个块级元素自闭合边界干净，不要依赖连续空 `<p>` 撑间距（空标签会剥，见第 5 条）；
- **深色模式智能反色**：微信 App 端对正文有自动反色机制，暖色系在深色下可能翻车 → 橙墨提供「深色模拟」预览（`invert(1) hue-rotate(180deg)` 近似），只作用于预览、不进复制内容，发布前可提前目检。
